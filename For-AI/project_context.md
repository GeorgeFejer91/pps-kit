# Project Context

## Aims

The toolkit should make audio-tactile PPS experiments reusable, reproducible, and publishable. The near-term aim is a ready-to-use Windows app for Study 5 and closely related audio-tactile PPS designs. The broader aim is a single program that can recreate published audio-tactile PPS paradigms by configuring stimuli, trial structure, runner behavior, and analysis settings.

## Audience

Primary users are cognitive neuroscience and psychology researchers who need to run, replicate, or adapt audio-tactile PPS experiments without editing Python scripts. Secondary users are developers and AI agents maintaining the toolkit.

## In Scope

- Generated or imported looming/prestimulus audio assets.
- Noise definitions, azimuth/elevation, SOFA/HRIR planning, trajectory radius/path/speed, and tactile cue timing.
- Trial design with repetitions, SOAs, spatial values, tactile sites, catch/baseline settings, blocks, and participant schedules.
- Automatic reproducible randomization in the background.
- Windows experiment running, audio/tactile channel routing, event/LSL marker recording, optional local audio evidence WAVs, physical-loopback validation, and local session outputs.
- Low-latency audio-device stress testing for synchronized binaural left/right plus tactile output.
- Loopback decoding and deidentified sample analysis.
- Study templates for published audio-tactile PPS paradigms when publication metadata is sufficient.
- Documentation and release audits that support a public GitHub repository.

## Out Of Scope

- Raw participant recordings or name-bearing outputs in Git.
- Generated participant WAVs and local session artifacts in Git.
- APKs, VR source code, or headset-specific app builds unless a future project explicitly adds them.
- Redistribution of SOFA/HRIR files, background music, proprietary sound sets, or other third-party assets unless rights are verified.
- Full visual/VR/social PPS reconstruction unless those details directly affect audio-tactile timing, spatial audio, tactile cues, responses, or analysis.

## Current Architecture

- Public CLIs are `pps-generate`, `pps-design`, `pps-dashboard`, `pps-render-design`, `pps-audio-stress`, `pps-latency-validate`, `pps-decode`, and `pps-analyze`. The only active operator experiment runner is the packaged `dist\PPSExperimentRunner\PPSExperimentRunner.exe`; `focus_app.py` remains the exe implementation and validation import target, not a separate public runner CLI, and direct module launch exits with retirement guidance. The old `pps-run`/Tk participant runner is no longer a public entry point.
- `configs/` contains example experiment and stimulus-design settings.
- `Example-configs/` may contain reference archives for external-study stimulus-generation materials; verify redistribution rights before treating any bundled third-party WAVs or scripts as public release assets.
- `study_templates/` contains preloadable literature-backed template JSON files.
- `assets/` contains only small owned seed assets intended for publication.
- `assets/preloads/` contains the public preload asset inventory and the segment-mirrored preload catalog. ## GUI Direction

The GUI should be researcher-friendly and should not expose implementation details as primary design choices. Users should define the experiment they want; the toolkit should handle reproducible mechanics such as randomization, participant block-order schedules, and validation in the background.

Randomization is documentation-relevant, not a normal GUI tool. The intended default is no-immediate-repeat trial ordering within blocks and counterbalanced participant block order, supporting any number of user-defined blocks.

The standard researcher-facing GUI is now the local HTML dashboard. It is launched with `pps-dashboard` or `windows\Launch_HTML_Dashboard.bat`, binds to `127.0.0.1`, opens in the user's default browser, and uses a small FastAPI backend to call the existing Python design, render, session-preparation, audio-stress, and packaged experiment-runner paths. This browser dashboard is not an online service and should not move validated participant timing into browser JavaScript; Segment 6 now materializes a participant session package and launches `PPSExperimentRunner.exe` for timing-sensitive native participant runs from prepared session manifests.

The dashboard should behave as a one-page local app: a fixed floating left rail, smooth section navigation, and user-adjustable panel sizing through direct workspace splitters/gutters and panel-edge handles rather than left-rail sliders. The workflow has one centralized page scroll surface: visible Segments and their panels should expand with content rather than creating their own vertical or horizontal scroll controls; resized panels use the stored size as a minimum height, and Segment 2 filmstrip rows wrap boxes instead of scrolling sideways. Visible segment headings should be short prose labels, not registry folder slugs: Segment 0 `Choose or Create Study`, Segment 1 `Build Looming Stimuli`, Segment 2 `Trial Sequence Design`, Segment 3 `Baseline and Tactile Trial Design`, Segment 4 `Trial Repetition Pool`, Segment 5 `Generate and Review Blocks`, and Segment 6 `Prepare Experiment`. Each visible segment heading should include an `About` description control whose modal explains purpose, expected user inputs, backend folder/manifest work, and how outputs feed the next step; backend folder names belong there rather than in the heading. Custom mode is not an open-ended freeform page; selecting `Custom design (define manually)` should force the researcher through the visible numbered HTML Segments in order. Segment 6 is the final visible dashboard segment; do not reintroduce a separate Segment 7 Review page unless the user explicitly asks for it. Render/prepare/run actions must stay locked until the custom design contains the minimum runnable profile fields.

Loaded profile/preload projects are read-only reference projects in the HTML dashboard and backend API. Their editable controls and bake/regenerate/prepare actions should remain locked, while Open Folder actions stay available for local inspection. Editing a profile is a left-rail mode switch: the `Edit As New Study` button opens an in-dashboard overlay requiring a new study name, then creates a timestamped custom project folder, copies active Segment 1 working-copy ingredients into that new folder, stores the source profile ID in project metadata, leaves the profile/preload project unchanged, and re-enables editing controls for the new custom study. Custom project folder IDs use compact, hash-suffixed slugs for long study names; the full study name remains the human-facing project label. Read-only edit attempts should open the same naming overlay rather than silently editing the profile, and direct `/api/design` profile mutations should be rejected. Segment 0 also exposes an `Existing custom study` selector backed by the local project registry so saved custom projects can be reopened without rebaking or clearing Segment 1-6 artifacts. In custom mode, workflow completion is artifact-based rather than field-only: later segments unlock only after the upstream manifest has been baked/accepted/prepared and validated. Upstream custom rebakes should warn about downstream invalidation.

The HTML dashboard should remain a set of visible, numbered Segments, with each Segment implemented as its own HTML section and containing only the controls for that decision cluster. Segment 0 owns published preload versus custom design and study-level naming; it activates or creates the writable project folder under `local_data/dashboard_projects/0_study_project_registry/` (`profile_<template_id>` or `custom_<project_name_slug>_<YYYYMMDD_HHMMSS>`). Segment 1 is a three-box workspace: `Trajectory And Source` and `Trajectory Preview` share the top row with a splitter-controlled width ratio, while `Stimulus Type Selection` spans the full width below them and displays the starting Segment 1 stimulus pool in two columns. The dashboard should not show generic registry-feedback panels or visible `Status`/`Ingredients`/`Variants`/`WAVs`/`Folder`/`Message` summary-row blocks in any segment; keep registry state in backend manifests and surface only the compact status chips, previews, and Open Folder buttons that support the current decision. Generated/imported core auditory ingredients are written under the active project's `1_core_audio_ingredients/` with content descriptors such as `inhale4000ms.wav` or `pink_frontal_looming4000ms.wav`. Segment 2 owns row-level within-trial sequence composition only. Its custom-design starting state is completely empty except for a single plus control; pressing plus creates the first row with one empty audio box, and later plus controls add ordered boxes or independent rows. An audio box contains saved custom clips and baked source labels as a vertical one-by-one list; one label is fixed, multiple labels are alternatives that multiply that row's variants. A box can be toggled into a jitter box, where the researcher enters one millisecond value per line. Boxes are concatenated left-to-right and crossed by Cartesian product; rows are independent trial families that add together and preserve visual row order for scheduling/interleaving. Do not put repetitions, block count, SOA count math, per-source counters, baseline counters, catch counters, or trial-total summaries in Segment 2. Pressing `Bake Trial Sequences` materializes the current row variants as derived WAVs under the active project's `2_trial_sequence_designs/`, with one row subfolder per trial family plus JSON/CSV manifest rows mapping files back to row id, source labels, jitter values, sequence labels, segment timing, scheduler variant key, file path, duration, and hash. Segment 2 WAV filenames should be minimal content descriptors plus timing, such as `inhale4000ms_pinklooming4000ms_total8000ms.wav` or `inhale4000ms_jitter500ms_pinklooming4000ms_total8500ms.wav`; row numbers belong in folders/manifests, not WAV names. The backend stores this as `protocol.trial_strips` with compatible `fixed_audio`, `jitter`, and `looming_stimulus` element kinds, but visible UI language should use boxes/audio pools rather than randomizer terminology. Segment 3 owns SOA entry, baseline strategy checkboxes, custom baseline timing/mode controls, and the Baseline/Tactile Trial bake. Segment 3 preserves row lineage by writing one top-level folder per Segment 2 row, such as `row_01__inhale_trial_type/` and `row_02__exhale_trial_type/`; each row folder contains leaf folders `target_audio_tactile/`, `baseline/`, and, when enabled, `catch_trials/`. Target and baseline WAVs are 3-channel with tactile in channel 3; catch WAVs are audio-only copies for later use. Segment 3 WAV names should stay minimal but identity-preserving, for example `inhale4000ms_pinklooming4000ms_soa300ms_tac120ms_total8000ms_ch3.wav` and `baseline_silent_inhale4000ms_pinklooming4000ms_soa300ms_tac120ms_total8000ms_ch3.wav`. Segment 4 owns the trial repetition pool: it reads the Segment 3 manifest, lets users set global, per-folder, and optional per-WAV repetition counts in non-negative 0.5 increments, shows live top-level trial/family counts in the left calculator, and uses the right Pool Oversight panel for read-only audio-tactile/baseline/catch percentage sliders with nested Inhale/Exhale sub-sliders plus a compact duration calculus that shows summed `duration_ms x reps`, total duration, and average trial duration. Whole-number repetitions repeat every eligible Segment 3 file; `.5` repetitions add deterministic balanced extra rows across family, row/phase, SOA, and source lineage while minimizing divergence. Segment 4 writes `4_trial_repetition_pool/trial_repetition_pool.csv` plus `trial_repetition_pool_manifest.json` without duplicating WAV files, but the dashboard does not render a visible CSV/pool preview table. Study 5 preloads Segment 4 with audio-tactile `3.0`, baseline `1.5`, and catch `3.0`, yielding 204 planned rows from the 88 Segment 3 files. Segment 5 owns block CSV generation and preview. It consumes only the Segment 4 trial-pool CSV, writes `5_block_csv_preview/block_XX.csv` files plus `block_csv_preview_manifest.json`, shows progress while CSVs are written, renders one collapsible color-coded CSV preview per block, and uses bottom `Regenerate Blocks` plus `Accept Blocks`/`Edit Blocks` decision controls. Segment 5 preview columns should expose recurring distribution features separately: family, row, SOA, noise type, sequence, duration, and WAV identity; SOA coloring uses one continuous gradient across the available SOA range, while family, row, and noise use categorical colors. Source lineage remains available internally for balancing, but is not exported or previewed as its own Segment 5 column unless explicitly requested. Visible Segment 6 is named `Prepare Experiment` and owns final experiment-level parameters plus the native Focus Mode handoff: planned participant count, 1-part versus 2-part/pre-post experiment structure, a preview table of participant-by-part block-order permutations, `Regenerate Sequence`, and `Save Design and Start Experiment Runner`. Segment 6 still writes `6_experiment_run_setup/experiment_block_order.csv` and `experiment_run_setup_manifest.json`; once prepared, it should not be silently overwritten. The final Segment 6 button locks the design/run setup, materializes the selected participant's session package, and launches packaged `PPSExperimentRunner.exe` from the local companion backend without capture-option flags. Participant metadata, optional fail-safe local recording, and per-part missed-trial top-up choices belong to Focus Mode / `PPSExperimentRunner.exe`; `events.csv`, local marker mirrors, trigger dictionary, and standard analysis outputs remain runner-owned outputs.

Segment 0-4 registry actions are now explicit and button-owned. Segment 0 uses `Apply Profile / Create Project Folder`, Segment 1 uses `Bake Ingredient`, Segment 2 uses `Bake Trial Sequences`, Segment 3 uses `Bake Baseline/Tactile Trials`, and Segment 4 uses `Bake Trial Pool CSV`. Registry status stays in backend state/manifests; do not add generic output/status summary panels to any segment. Every Segment 0-4 stage keeps an `Open Folder` action backed by `/api/state.project_segments`. Segment 1 actions may invalidate downstream outputs but must not secretly bake Segment 2. Segment 2 validates registered Segment 1 paths, hashes, durations, and channel counts before writing. Segment 3 refuses missing/stale Segment 2 manifests and records the consumed Segment 2 manifest hash plus its own timing/baseline design signature. Segment 4 refuses missing/stale Segment 3 manifests, records the consumed Segment 3 manifest hash, and writes CSV/JSON only.

Segment 5 row order is a hard structural invariant. Segment rows are not free randomization categories: they are the within-block sequence scaffold created by Segment 2 and preserved by Segment 3 folders. Segment 5 may randomize which concrete trial appears in each row slot, but every generated block must cycle through the preserved row order. For Study 5 this means inhale, exhale, inhale, exhale until the block is complete.

Current Segment 5 GUI behavior uses two bottom decision buttons only. `Regenerate Blocks` reruns the row-order-preserving randomization with a fresh seed and overwrites the current unaccepted `5_block_csv_preview/block_XX.csv` candidate files. `Accept Blocks` finalizes the current candidate by renaming those CSVs to `block_XX_final.csv`, marks the manifest accepted, locks Segment 5 against regeneration/upstream overwrites, and unlocks Segment 6 Prepare Experiment. After acceptance, the same control becomes `Edit Blocks`; pressing it restores the working `block_XX.csv` names, clears the accepted flag, and reopens Segment 5 for changes. The first block preview should open by default and each block header should show a triangle/caret dropdown affordance.

Current Segment 6 GUI behavior is deliberately decluttered. It has two top decisions, `Planned participants` and `Experiment parts` (`1 part` or `2 parts`), followed by a **Preload Instruction Audio Clips** panel, `Block Permutation Preview` table, and bottom actions. The instruction panel owns optional run-level messages only: before experiment, before each block, after each block, between conditions, and after experiment, each with enable/path metadata plus click, timed-delay, or runner-button continuation. Empty, missing, disabled, or changed instruction slots are not Segment 6 blockers and must not disable the final runner action; they are skipped with warnings when needed. Segment 2 remains the owner of within-trial instruction snippets such as Study 5 inhale/exhale clips. `Regenerate Sequence` changes only the block-order permutation seed while the setup is not prepared. `Save Design and Start Experiment Runner` writes the final participant/phase/block-order CSV and manifest under `6_experiment_run_setup/`, records the accepted Segment 5 manifest hash, locks the prepared setup against silent overwrites, and calls the local backend route that starts the PC runner program. After preparation, the same final control becomes `Open Experiment Runner` and reopens the local runner without rewriting Segment 6. A pre/post setup gives every participant one pre order and one post order of the accepted final block CSVs; the Study 5 dashboard default uses this two-condition setup and shows user-facing labels `Condition 1` and `Condition 2` while preserving internal `pre`/`post` phase values.

The Segment 5/6 runner contract is now participant-level block WAV synthesis. Segment 5 is the master block CSV library; Segment 6 is the authoritative participant/phase block-order table. The HTML dashboard materializes the selected participant's ordered session under `local_data/sessions/<participant_id>_<timestamp>/`, then launches native PySide Focus Mode through packaged `dist\PPSExperimentRunner\PPSExperimentRunner.exe --session-manifest <session_manifest.json>`. The Focus Mode window inside that exe is the only public participant runner surface: a light dashboard-styled PySide app shell with PPS icon identity, participant/session/block status, instruction-clip status, participant metadata fields, runner-owned recording controls, a large response target, progress controls, top-up approval, and output summary.
