# Project Context

## Aims

The toolkit should make audio-tactile PPS experiments reusable, reproducible, and publishable. The near-term aim is a ready-to-use Windows app for Study 5 and closely related audio-tactile PPS designs. The broader aim is a coherent PPS Toolkit product with a central hub and independently runnable applets for design/stimulus generation, native acquisition, Android control or experimental phone execution, analysis/review, and calibration. These applets should share a versioned core/workspace rather than depend on each other's GUI internals. This modular release direction may support a future JOSS paper in addition to the existing Behavior Research Methods manuscript direction.

Latest source-to-runner validation status, 2026-07-15: `serino_2015_toolless_sync_training` is now a verified runnable published profile, not a missing-parameter scaffold. Frontiers publisher-source review captured the one-block PPS assessment profile: 3000 ms IN/OUT pink-noise sounds, near/far hidden loudspeakers, right-hand DS7A electrical tactile target context, vocal response capture, T1-T5 tactile delays at 300/800/1500/2200/2700 ms, a printed 77% tactile-target rate, and the expected synchronous-training PPS extension without tool use. The paper-specific validator produced a runnable 104-row WAV/session package, software loopback sidecar, and mouse-click simulated participant-like rows preserving 80 tactile-target trials plus 24 auditory-only catches. Current machine ledgers report 30 templates, 24 ready profiles, 22 published ready profile variants, 6 current missing-parameter profiles, 17 covered runnable literature records, and 17 full emulated source-to-runner validations; older same-day count paragraphs below are historical checkpoints when they cite lower counts.

## Audience

Primary users are cognitive neuroscience and psychology researchers who need to run, replicate, or adapt audio-tactile PPS experiments without editing Python scripts. Secondary users are developers and AI agents maintaining the toolkit.

## In Scope

- Generated or imported looming/prestimulus audio assets.
- Noise definitions, azimuth/elevation, SOFA/HRIR planning, trajectory radius/path/speed, and tactile cue timing.
- Trial design with repetitions, SOAs, spatial values, tactile sites, catch/baseline settings, blocks, and participant schedules.
- Automatic reproducible randomization in the background.
- Windows experiment running, audio/tactile channel routing, event/LSL marker recording, optional local audio evidence WAVs, physical-loopback validation, and local session outputs.
- Low-latency audio-device stress testing for synchronized binaural left/right plus tactile output.
- Loopback decoding and deidentified sample analysis.
- Study templates for published audio-tactile PPS paradigms when publication metadata is sufficient.
- Documentation and release audits that support a public GitHub repository.
- A public-safe, interactive map of experimental audio-tactile PPS publications
  whose paradigms are covered by the Toolkit literature audit.

## Out Of Scope

- Raw participant recordings or name-bearing outputs in Git.
- Generated participant WAVs and local session artifacts in Git.
- Generated APKs or headset-specific app builds unless a future release explicitly adds them; the native Android runner companion source is now in scope as a local phone companion for Focus Mode.
- Redistribution of SOFA/HRIR files, background music, proprietary sound sets, or other third-party assets unless rights are verified.
- Full visual/VR/social PPS reconstruction unless those details directly affect audio-tactile timing, spatial audio, tactile cues, responses, or analysis.

## Current Architecture

- The agreed target product architecture is recorded in `For-AI/product_applet_architecture.md`. The hub is a launcher and status surface, not a scientific or timing authority. Applets should remain independently launchable and exchange profiles, manifests, assets, and prepared experiments through shared public schemas/APIs. This is a target boundary: current large facades and runner-to-dashboard private-helper dependencies still require behavior-preserving extraction.
- Package-supplied study templates are immutable, versioned, read-only release resources. A user who customizes one must receive a new provenance-linked custom profile before the first change is applied. Editable profiles remain drafts; preparation creates an immutable runnable snapshot, and later edits require a new prepared revision. The prepared-experiment package is the intended stable handoff among designer, runner, Android phone-local runtime, validator, and archive.

## GUI Direction

The GUI should be researcher-friendly and should not expose implementation details as primary design choices. Users should define the experiment they want; the toolkit should handle reproducible mechanics such as randomization, participant block-order schedules, and validation in the background.

Randomization is documentation-relevant, not a normal GUI tool. The intended default is no-immediate-repeat trial ordering within blocks and counterbalanced participant block order, supporting any number of user-defined blocks.

The standard researcher-facing GUI is now the local HTML dashboard. It is launched with `pps-dashboard` or `windows\Launch_HTML_Dashboard.bat`, binds to `127.0.0.1`, opens in the user's default browser, and uses a small FastAPI backend to call the existing Python design, render, session-preparation, audio-stress, and packaged experiment-runner paths. This browser dashboard is not an online service and should not move validated participant timing into browser JavaScript; Segment 6 now materializes a participant session package and launches `PPSExperimentRunner.exe` for timing-sensitive native participant runs from prepared session manifests.

Segment 0 can designate a local data acquisition folder through the companion backend action `/api/data-acquisition/export`. That action creates or reuses an experiment-named output project and creates the protected `Experiment_context_folder_DO_NOT_DELETE/` context folder. New operational files are split by role: `project_state/` owns `output_diary.v1.jsonl` and `dashboard_runner_bridge_manifest.v1.json`, `runner_logs/` owns the append-only `<experiment_slug>_LOG-DIARY_DO_NOT_DELETE.txt` diary and per-session/per-part runner metadata/manifests plus LabRecorder capture diagnostics, `profile_snapshot/` owns copied dashboard/profile snapshots, `shared_instructions/` owns copied run-level instruction WAVs once per environment, `prepared_blocks/` owns reusable generated block CSV/WAV package assets, and `verbose_events/` owns debugging/reconstruction mirrors such as `events.csv`, internal XDF mirrors, local LSL marker mirrors, and trigger dictionaries. The runner and dashboard still read legacy `study_profile_snapshot_DO_NOT_DELETE/`, `study_profile_snapshot/`, and root-level marker files so existing output folders remain resumable. Participant folders belong beside the context folder and should stay researcher-facing. New two-part Segment 6 preparations create one session group folder `<participant_id>_<timestamp>/` with child `part_01/` and `part_02/` folders; each child part folder contains that part's primary `<part_session_id>_trials.csv`, optional runner-owned part-local `<part_session_id>_external_labrecorder.xdf`, per-block audio-evidence WAVs, and optional wired-loopback WAVs. A same-window Part 1 -> Part 2 LabRecorder continuation instead finalizes one group-level `<session_group_id>_external_labrecorder.xdf` beside the child part folders. Context outputs mirror the same group/part leaf, for example `runner_logs/<session_group_id>/part_01/session_manifest.json`, `verbose_events/<session_group_id>/part_01/events.csv`, and `Data_Analytics/<session_group_id>/part_01/`, with same-window continuous LabRecorder diagnostics under `runner_logs/<session_group_id>/`. Legacy unsplit packages continue to use `<session_id>/` leaves. The diary is an orchestration/index log for button actions, profile saves/selections, acquisition-folder exports, package preparation, runner events, completion/interruption, and output summaries; it does not replace per-session evidence files or the participant trial CSV.

The dashboard should behave as a one-page local app: a fixed floating left rail, smooth section navigation, and user-adjustable panel sizing through direct workspace splitters/gutters and panel-edge handles rather than left-rail sliders. The workflow has one centralized page scroll surface: visible Segments and their panels should expand with content rather than creating their own vertical or horizontal scroll controls; resized panels use the stored size as a minimum height, and Segment 2 filmstrip rows wrap boxes instead of scrolling sideways. Visible segment headings should be short prose labels, not registry folder slugs: Segment 0 `Choose or Create Study`, Segment 1 `Build Looming Stimuli`, Segment 2 `Trial Sequence Design`, Segment 3 `Baseline and Tactile Trial Design`, Segment 4 `Trial Repetition Pool`, Segment 5 `Generate and Review Blocks`, and Segment 6 `Profile Validation and Save`. Custom mode is not an open-ended freeform page; starting a custom design forces the researcher through visible numbered Segments in order and invalidates downstream reviews after upstream edits.
