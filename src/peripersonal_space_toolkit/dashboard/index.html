PPS Toolkit Public Documentation

Project

Project In A Nutshell

The Peripersonal Space Toolkit is a local-first research program for designing, validating, and running audio-tactile peripersonal-space experiments. It turns a study profile or custom design into spatialized looming audio, tactile timing schedules, block CSVs, participant session packages, and native experiment-runner outputs that can be inspected and reproduced.

What The Website Is

This dashboard is the user interface and orchestration layer. It collects researcher decisions, previews study structure, and asks the local companion to do work on the research PC.

What The Backend Does

The local Python companion handles file imports, stimulus rendering, project folders, session preparation, audio-device checks, and native runner launch. Timing-sensitive work stays out of browser JavaScript.

Who It Is For

The main audience is cognitive neuroscience and psychology labs that need reusable audio-tactile PPS designs without editing Python scripts for every experiment.

Software Layers

Architecture And Dependencies

The project should be understood as a UI layer sitting on top of a Python experiment engine. The dashboard provides the visible workflow; the package code owns rendering, audio routing, validation, runner setup, and analysis outputs.

Science And Audio

numpy, scipy, soundfile, and sounddevice support numerical audio work, WAV I/O, and low-latency playback. sofar and netCDF4 support SOFA/HRIR resources.

UI And Companion

The browser dashboard talks to a local FastAPI and Uvicorn companion. The native desktop runner uses PySide6 through the packaged PPSExperimentRunner.exe.

Timing And Recording

pylsl and pyxdf support marker streams and XDF reconstruction. Windows diagnostics may use pyaudiowpatch, but the validated multichannel experiment route uses ASIO.

Packaging

PyInstaller builds the native runner. The public release path uses a small Windows downloader plus a verified offline lab package.

Rendering Resources

The current binaural workflow uses the bundled FABIAN/TU SOFA HRIR resource and can produce outputs through the native 3DTI route or the Python SOFA/FABIAN reference renderer.

Deep References

Detailed setup and operating notes live in the repository documentation.

Stimulus Model

SOFA/FABIAN And Spatialized Looming Stimuli

SOFA, the Spatially Oriented Format for Acoustics, stores spatial acoustic measurements such as head-related transfer functions. In this toolkit, the bundled FABIAN/TU SOFA HRIR resource is the standard binaural rendering reference, and the dashboard keeps it under the hood so routine experiment design focuses on trajectory, timing, and trial structure.

  1. The researcher chooses a study profile or custom design, then defines source material, looming duration, start/end distance, direction, rotation, and timing choices.
  2. The local backend converts those decisions into trajectory samples and render metadata rather than relying on filenames or browser-only state.
  3. The renderer creates binaural auditory material for channels 1 and 2, while tactile cue placement is introduced later from the SOA schedule into channel 3.
  4. Generated manifests record the render config, trajectory samples, tactile events, file hashes, and quality-control summaries so the stimulus path can be audited.

SOFA Standard

SOFA is an AES-standardized format for spatial acoustic data, including HRTFs and binaural room impulse responses.

Native Renderer

3DTI Rendering Toolkit

3DTI, the 3D Tune-In Toolkit, is the original open-source C++ spatial-audio renderer that established the binaural rendering path used by this project. The original 3DTI repository now points developers to the newer BRT Library, the Binaural Rendering Toolbox, because the authors migrated the algorithms there and recommend BRT for ongoing support. PPS Toolkit therefore treats the original 3DTI repository as publication/provenance history and uses the newer BRT lineage as the forward-facing recommended GitHub source, while preserving existing 3DTI-compatible configs and pinned source snapshots for reproducibility.

Lab Route

Hardware Specifications And Latency Evidence

The validated lab route is Windows-first and uses one synchronized multichannel ASIO output path. The current wiring convention is channel 1 to left auditory output, channel 2 to right auditory output, and channel 3 to the tactile drive path.

Komplete Audio 6 MK2

The lab route uses Native Instruments Komplete Audio 6 MK2 as the synchronized multichannel interface.

Open NI Drivers Page

Komplete ASIO Driver

Use the official Komplete Audio ASIO Driver on Windows. The stereo Windows endpoints are legacy/diagnostic paths, not the validated 3-channel route.

Open ASIO Install Guide

Woojer Strap

The tactile target is treated as a wired analog endpoint from Komplete output 3. Bluetooth should not be used for timing-sensitive tactile work.

Design Workflow

How The Experiment Designer Works

The Experiment Designer is a segmented workflow. It starts with study/profile selection, then moves through stimulus ingredients, trial sequences, tactile/baseline files, repetition pools, block CSV previews, and final experiment setup. Each segment is meant to own one decision layer and one set of local files/manifests.

0 PreloadChoose a published profile or custom project.
1 StimuliCreate or import reusable auditory ingredients.
2 SequenceArrange ingredients into within-trial rows and variants.
3 TactileAdd SOAs, baseline logic, catch files, and channel-3 tactile cues.
4 PoolSet repetition counts and write the trial-pool CSV.
5 BlocksGenerate, inspect, and accept block CSVs.
6 PrepareCreate participant block orders and hand off to the native runner.

Native Runtime

How The Experiment Runner Works

The Experiment Runner is the native Focus Mode application launched from the prepared Segment 6 setup. It owns timing-sensitive playback, participant metadata, response logging, LSL/event markers, optional local audio evidence WAVs, top-up behavior, and session outputs.

  • Segment 6 prepares the run setup and selected participant session package.
  • The runner opens the packaged PPSExperimentRunner.exe, not a browser timing loop.
  • Playback uses the validated ASIO route with one persistent output stream for auditory and tactile channels.
  • Session folders receive event CSVs, local XDF/marker mirrors, trigger dictionaries, timing QC, analysis-ready trial rows, and summary outputs.

Public Release

Data, Privacy, And Publication Boundary

The public repository contains the toolkit, documentation, deidentified samples, safe templates, and release metadata. Participant data, generated participant WAVs, raw recordings, local validation artifacts, downloaded model caches, and unreviewed third-party assets stay in ignored local folders.

Local Data

Generated designs, sessions, participant outputs, and validation artifacts are written locally under ignored folders such as local_data/ and artifacts/.

Hosted Dashboard

The GitHub Pages dashboard is still only a front end. It connects to 127.0.0.1 after the user starts the trusted local companion.

Third-Party Assets

SOFA/HRIR files, vendor manuals, background audio, and proprietary stimuli require attribution and redistribution review before release packaging.
